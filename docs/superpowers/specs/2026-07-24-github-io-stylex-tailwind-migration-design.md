# GitHub.io StyleX and Tailwind Migration Design

## Goal

Migrate `apps/github.io` away from app-wide component CSS as the primary styling model and toward the Astryx styling overview:

- StyleX for component-specific overrides, reusable local styles, pseudo-classes, and typed token access.
- Tailwind utilities for layout, wrappers, spacing composition, and utility styling.
- `className` for passing Tailwind utilities or external CSS integration into components.
- Styling-library token aliases for any future non-Tailwind styling system, with Astryx tokens remaining the source of truth.

The migration should preserve the current UI behavior while making future React component styling follow Astryx-supported conventions.

## Current State

The app already uses Astryx as the design system:

- `@astryxdesign/core`, `@astryxdesign/theme-neutral`, and `@astryxdesign/cli` are installed.
- `apps/github.io/src/main.tsx` imports Astryx reset, base CSS, and neutral theme CSS.
- `AppShell` wraps the app in Astryx `Theme`.
- App components use Astryx primitives such as `Avatar`, `Badge`, `Citation`, `EmptyState`, `List`, `ListItem`, `PowerSearch`, and `VisuallyHidden`.

App-specific styling currently lives mostly in `apps/github.io/src/styles.css` through global selectors such as `.page`, `.skill-list`, `.skill-token`, `.skill-rating`, `.certification-citation`, `.devops-roadmap-node`, and `.devops-roadmap__flow`.

## Recommended Architecture

Use a three-layer styling architecture for `apps/github.io`.

### Global CSS

Keep `styles.css` only for true global app rules and third-party CSS integration:

- `html`, `body`, and global element defaults such as anchor inheritance.
- Required cascade layer declarations and imports for Astryx, Tailwind, and generated StyleX CSS.
- React Flow selectors that must target third-party DOM generated by `@xyflow/react`, unless a stable component-level API can replace them.

Global CSS must continue to use Astryx CSS custom properties for theme-aware values.

### Tailwind

Use Tailwind utilities for layout, wrappers, and simple utility styling:

- Page width, margins, padding, grid/flex layout, gaps, wrapping, min-width, and responsive layout changes.
- Utility classes passed through `className` to Astryx components when the Astryx docs identify `className` as the integration surface.
- Tailwind utilities backed by `@astryxdesign/core/tailwind-theme.css`, so names such as text, surface, border, radius, spacing, and shadow resolve to Astryx tokens.

Do not introduce hardcoded Tailwind theme values that duplicate Astryx colors, spacing, radius, typography, or shadows.

### StyleX

Use StyleX for component-specific styling and overrides:

- Local component states and variants, such as skill token variants and certification citation branded states.
- Reusable local style objects shared by a component and its story/test helpers when needed.
- Pseudo-classes or state selectors that belong to one component.
- Astryx component overrides through the `xstyle` prop.

StyleX styles should reference Astryx CSS variables or Astryx typed StyleX token exports. Brand-driven inline CSS variables may remain where the value is content data rather than a design-system token, such as external product logo colors.

## Build Configuration

Add explicit StyleX build support for the Vite app:

- Add `@stylexjs/stylex` as a direct dependency because app code will import it directly.
- Add `@stylexjs/unplugin` as a dev dependency.
- Add Tailwind v4 as a dev dependency so layout and utility styling can follow the Astryx Tailwind bridge path.
- Configure `apps/github.io/vite.config.ts` with `stylex.vite(...)` before `react()`.
- Keep one app CSS entry imported from `main.tsx` so Vite emits a CSS asset for StyleX output.

Use CSS layers deliberately so Astryx, StyleX, and Tailwind precedence is predictable. The intended order is:

1. Reset/base layers.
2. Astryx base and theme layers.
3. StyleX component styles.
4. Tailwind utilities.

Implementation should consolidate Astryx and Tailwind stylesheet imports into `styles.css` with an explicit layer prelude based on Astryx's documented Tailwind bridge pattern:

```css
@layer reset, theme, base, astryx-base, astryx-theme, stylex.priority1, stylex.priority2, utilities;

@import "tailwindcss/theme.css" layer(theme);
@import "tailwindcss/preflight.css" layer(base);
@import "@astryxdesign/core/reset.css";
@import "@astryxdesign/core/astryx.css";
@import "@astryxdesign/theme-neutral/theme.css";
@import "@astryxdesign/core/tailwind-theme.css";
@import "tailwindcss/utilities.css" layer(utilities);
```

Configure `stylex.vite({ useCSSLayers: { before: ['reset', 'theme', 'base', 'astryx-base', 'astryx-theme'], after: ['utilities'], prefix: 'stylex' } })`, adjusting only if the installed plugin version documents different generated priority layer names.

## Migration Scope

This initial migration should touch existing styling enough to establish the pattern:

- Add Tailwind and StyleX dependencies and Vite configuration.
- Move Astryx stylesheet imports from `main.tsx` into `styles.css` alongside the Astryx Tailwind bridge and Tailwind imports.
- Convert app shell and simple layout wrappers from global CSS classes to Tailwind utilities.
- Convert component-specific selectors from `styles.css` to StyleX in the owning components.
- Keep third-party React Flow selectors global if they cannot be expressed safely through component props.
- Reduce `styles.css` to globals, imports, layer declarations, and third-party integration.

The migration should not redesign the UI, change content, change routing, or replace Astryx components.

## Component Boundaries

Prefer colocated styles in the component file for small components. Extract a sibling style module only when the style object becomes large enough to distract from component behavior.

Expected ownership:

- `AppShell`: page layout classes become Tailwind utilities.
- `SkillSection` and `SkillList`: wrapper/header/list layout becomes Tailwind utilities unless an Astryx component override needs StyleX.
- `SkillListItem`, `SkillToken`, `SkillRating`, `SkillAvatar`, and `SkillCategory`: component-specific appearance moves to StyleX or Astryx `xstyle`.
- `CertificationCitation`: component-specific source sizing and branded/expired behavior moves to StyleX, while data-driven brand color CSS variables can remain inline.
- `DevopsRoadmap` and `DevopsRoadmapNode`: node card styling moves to StyleX; React Flow internals remain global if needed.

## Testing and Validation

Required validation after implementation:

- `pnpm nx test github.io`
- `pnpm nx build github.io`
- Storybook-focused checks if the project exposes a `github.io` Storybook target.
- Browser or screenshot verification for the skills list and DevOps roadmap views if styling changes are visually broad.

Current environment note: `pnpm` is not available in this shell, so baseline Nx commands could not run during design. Implementation should either activate pnpm through Corepack or document the blocker if package-manager execution remains unavailable.

## Risks

- StyleX Vite configuration can fail silently if generated CSS is not emitted or loaded; verify actual rendered styles, not just TypeScript success.
- CSS cascade layer ordering can make Tailwind utilities unexpectedly override or fail to override Astryx/StyleX styles.
- Migrating global selectors may break Storybook snapshots or tests that rely on class names.
- React Flow internal selectors are third-party integration points and should not be forced into StyleX unless the library exposes a stable alternative.

## Out of Scope

- Full visual redesign.
- Replacing Astryx with another component library.
- Creating a custom Astryx theme.
- Swizzling Astryx components.
- Adding another CSS-in-JS library beyond StyleX.
