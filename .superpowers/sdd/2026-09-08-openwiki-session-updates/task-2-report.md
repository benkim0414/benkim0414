# Task 2 report: OpenWiki repository integration

## Outcome

Installed `openwiki@0.5.0` exactly as a workspace-root development dependency,
approved only its observed native `better-sqlite3` build, installed the bundled
Codex skill project-locally, and configured the MCP server to resolve through
`pnpm exec`. No repository wiki pages or Claims metadata were generated by this
task.

## Installer inspection

- Package requires Node >=22 and exposes `dist/cli/cli.js` as `openwiki`.
- Project Codex targets are `.agents/skills/openwiki` and `.codex/config.toml`.
- The installer is transactional, preserves non-managed TOML, hashes the skill
  bundle in `.openwiki-install.json`, and reports modified managed content.
- Published default MCP command is global: `openwiki mcp --host codex`. The
  installer API was therefore used with `pnpm exec openwiki mcp --host codex`;
  the same portable command is recorded in config and receipt.
- The public setup CLI cannot accept a custom MCP command. Consequently,
  `pnpm openwiki:setup` is idempotent for upstream output but will restore the
  global command. To restore the local command after repair, run from repo root:

  ```sh
  node --input-type=module -e 'import { HostIntegrationInstaller } from "./node_modules/openwiki/dist/integrations/install/installer.js"; import { getHostTarget } from "./node_modules/openwiki/dist/integrations/install/registry.js"; await new HostIntegrationInstaller().install(getHostTarget("codex"), { scope: "project", root: ".", mcpServerCommand: { command: "pnpm", args: ["exec", "openwiki", "mcp", "--host", "codex"] } });'
  ```

## Runtime and lifecycle findings

- `openwiki --version` is unsupported; `pnpm exec openwiki --help` displays the
  `OpenWiki v0.5.0` banner.
- A real JSON-RPC initialize handshake returned MCP server 0.5.0, tool
  capabilities, and all six tools. Start it with
  `pnpm exec openwiki mcp --host codex` from the repository root.
- Keep one stdio MCP process connected for the entire lifecycle. Active session
  state is process-local. After reconnecting, call `openwiki_begin` to rebuild
  the active runtime from durable run state.
- Tool order/API: `openwiki_begin({root,mode:"update"})`,
  `openwiki_submit_plan({runId,pages,deletePages?})`,
  `openwiki_next_page({runId})`, optional
  `openwiki_inspect_page_claims({runId,jobId})`,
  `openwiki_submit_page({runId,jobId,confirmedClaimIds?,claims?,retractedClaimIds?})`,
  and `openwiki_finish({runId})`.
- Always bootstrap this repository with `mode: "update"`. Release 0.5.0 init
  invokes code-mode setup that creates `.github/workflows/openwiki-update.yml`,
  conflicting with the approved no-CI design. Update mode can accept new pages;
  the parent must confirm the real empty-wiki bootstrap through MCP.
- Release 0.5.0's generic managed AGENTS snippet mentions scheduled GitHub
  Actions irrespective of mode. Treat it as upstream generic text; no workflow
  is installed, and authored local guidance remains authoritative.

## Deterministic probes

- Two installs into `/tmp/openwiki-install-probe` produced `install` then
  `unchanged`; status returned `codex installed` and only the expected skill,
  receipt, and TOML paths were written.
- Source snapshot/changed-path probes used a temporary Git fixture. A clean
  initial commit returned no changed paths. An uncommitted tracked edit changed
  the fingerprint and returned `source.txt`. A later relevant commit returned
  `source.txt` from the earlier baseline. A tracked edit under an ignored path
  did not enter changed paths or the source fingerprint.
- The source implementation also enumerates untracked files and worktree status,
  excludes generated `openwiki/` paths from update windows, and permits a clean
  unchanged update to return `status: "noop"` after successful metadata exists.

## Remaining generation step

The parent owns real repository generation to respect sequential page authorship.
Use its persistent stdio client, call `openwiki_begin` with the absolute worktree
root and `mode: "update"`, submit the source-grounded page plan, process exactly
one returned page at a time, and call `openwiki_finish`. Do not claim completion
until finish returns `complete`; if update-mode empty-wiki bootstrap rejects,
stop and report the no-CI incompatibility rather than using init.
